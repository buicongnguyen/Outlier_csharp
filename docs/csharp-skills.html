1. C# Language & .NET Runtime

What actually happens between your source file and the CPU: the type system, the features that make C# feel like C# (generics, delegates, LINQ, async/await), and the managed runtime underneath — JIT compilation, the garbage collector, and the escape hatches for when allocation matters.

Key terms

CLR (Common Language Runtime)
The .NET virtual machine: loads assemblies, JIT-compiles IL to native code, manages memory (GC), enforces type safety, and handles exceptions.
IL / JIT
The C# compiler (Roslyn) emits Intermediate Language into assemblies; the JIT compiler translates IL to native machine code at run time, method by method, with tiered compilation re-optimizing hot paths.
Assembly
The unit of deployment and versioning: a .dll or .exe containing IL, metadata, and a manifest. NuGet packages ship assemblies.
Value type
struct, enum, and the built-in numerics: the variable is the data. Assignment copies the whole value; stored inline (stack, or inside its containing object).
Reference type
class, interface, delegate, string, arrays: the variable holds a reference to an object on the GC heap. Assignment copies the reference — both variables then point at the same object.
Boxing / unboxing
Wrapping a value type in a heap object to treat it as object (boxing), and casting it back out (unboxing). Silent, allocating, and a classic hidden cost — generics were added largely to avoid it.
Generics
Types and methods parameterized by type (List<T>): compile-time type safety without casts or boxing. Constraints (where T : IComparable<T>) let the body use members of T.
Delegate
A type-safe reference to a method (or several — delegates are multicast). Action<T> and Func<T,TResult> are the standard generic delegate types.
Event
A delegate field with restricted access: outside code can only subscribe (+=) and unsubscribe (−=); only the declaring class can invoke it. The language-level observer pattern.
Lambda / closure
x => x * 2 creates a delegate inline. Capturing a local variable creates a closure — the variable is lifted to a compiler-generated heap object shared by the lambda and the enclosing method.
LINQ
Language Integrated Query: composable operators (Where, Select, GroupBy…) over IEnumerable<T> (delegates, in-memory) or IQueryable<T> (expression trees, translated to SQL by providers like EF Core).
Deferred execution
A LINQ query is a description, not a result: nothing runs until you enumerate it (foreach, ToList(), Count()). Enumerating twice runs it twice.
Extension method
A static method invoked as if it were an instance method on its first (this-marked) parameter. How LINQ adds 50 operators to every IEnumerable without touching it.
async / await
Compiler-rewritten asynchrony: await suspends the method without blocking the thread, then resumes when the awaited Task completes. For I/O-bound work; CPU-bound work uses Task.Run.
Task / Task<T>
A promise of a future result (or completion). Not a thread — an I/O Task typically occupies no thread at all while waiting.
iterator (yield return)
A method that produces a lazy sequence one element at a time; the compiler builds the state machine. Backbone of custom IEnumerable implementations.
IDisposable / using
The contract for deterministic cleanup of non-memory resources (files, sockets, DB connections). using guarantees Dispose() runs even on exception — the GC alone gives no timely cleanup.
GC generations
The garbage collector partitions the heap: gen 0 (new, collected often, cheap), gen 1 (survivors), gen 2 (long-lived, collected rarely, expensive), plus the Large Object Heap (≥ 85 KB).
Nullable reference types
Opt-in compile-time null analysis: string means never null, string? means maybe null, and the compiler warns on unguarded dereference. Annotations, not runtime enforcement.
record
A type declared for its data: compiler-generated value-based equality, ToString, and non-destructive mutation via with. Records are immutable by convention (init-only properties).
Pattern matching
is patterns and switch expressions that test shape — type, properties, relations — and bind variables in one step: if (shape is Circle { Radius: > 0 } c).
Span<T> / Memory<T>
A safe view over a slice of contiguous memory (array, stack, native) without copying or allocating. Span is stack-only (ref struct); Memory can live on the heap and cross await boundaries.
String immutability
Strings never change after creation; every Concat/Replace/Substring makes a new one. Repeated concatenation in a loop is O(n²) allocations — use StringBuilder.

Core concepts

Value vs reference semantics

Assigning a struct copies the data; assigning a class copies the pointer. That is the whole difference — and the source of the classic bugs: mutating a struct you got from a property mutates the copy, not the original (which is why structs should be small and immutable); two class variables aliasing one object see each other's changes. == follows suit: reference identity for classes (unless overloaded, as string does), field-by-field only if you implement it — or use a record.

Generics beat object

List<int> stores ints inline: no boxing, no casts, and the JIT compiles a specialized version for each value type. The pre-generics alternative — collections of object — costs an allocation per element and a runtime cast per read. Constraints make generic code useful: where T : IComparable<T> lets you sort, where T : new() lets you construct, where T : class/struct pins the kind. Pitfall: T == comparisons and reflection-heavy generic code reintroduce the costs generics were meant to remove.

Delegates → events → LINQ

One idea builds on the next: a delegate is a method you can pass around; an event is a delegate only its owner may fire; a lambda is a delegate you write inline; LINQ is a library of methods taking those lambdas. Two pitfalls pay rent forever: an event subscription from a long-lived publisher keeps the subscriber alive (the classic .NET memory leak — unsubscribe or use weak patterns), and a captured loop variable is shared by all iterations' lambdas unless you copy it locally (fixed for foreach in C# 5, still true for for).

async/await mechanics

The compiler rewrites an async method into a state machine: code up to the first await runs synchronously; at the await, if the task isn't finished, the method returns to its caller and the rest is scheduled as a continuation. No thread sits blocked — that is why one server can hold thousands of pending requests. Rules that keep you safe: async all the way (blocking with .Result/.Wait() invites deadlocks in UI/legacy ASP.NET contexts), async void only for event handlers (its exceptions are uncatchable by the caller), and use Task.WhenAll to run independent work concurrently instead of awaiting sequentially.

GC reality and IDisposable

Allocation is cheap (pointer bump) and gen 0 collections are fast; cost comes from objects that survive into gen 2 or the LOH, and from mid-life objects that die just after promotion. The GC knows nothing about files, sockets, or connections — that's IDisposable's job, and using makes cleanup deterministic. Finalizers are a safety net, not a strategy: they delay reclamation by a full GC cycle and run on their own thread. Performance work in .NET is usually allocation work: measure with dotnet-counters/PerfView before touching code.

Modern C# idioms

Post-C#-8 code reads differently: records for DTOs and messages (value equality + with for change-a-copy), switch expressions with property patterns instead of if-chains, nullable reference types making "can this be null?" a compiler question, target-typed new(), and file-scoped namespaces. Span<T> sits at the performance end: parsing and slicing without substrings or copies. Idiomatic modern C# is immutable-by-default at the edges (inputs, messages) and mutable only where measured hot paths demand it.

Closure capture — why the loop prints 333

var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));      // prints 333, not 012!

what the compiler generates:                       HEAP
                                          ┌──────────────────────┐
   loop variable i ──── lifted into ────▶ │ DisplayClass         │
                                          │    int i;  // ONE i  │

2. Object-Oriented Design

Organizing code so it can change: encapsulation, polymorphism, and abstraction as C# expresses them, the SOLID principles as day-to-day decisions, and the design patterns that .NET itself is built from. The recurring theme: depend on abstractions, prefer composition, and keep reasons-to-change separated.

Key terms

Encapsulation
An object owns its state and exposes behavior, not fields: private data behind methods/properties, invariants enforced in one place. Access modifiers (private, internal, protected, public) are the mechanism.
Inheritance
A class extends a base class, reusing and specializing it: one base, single inheritance in C#. Models "is-a" — and couples the child to the parent's implementation decisions.
Polymorphism
Calling through a base type executes the runtime type's override: shape.Area() runs Circle's or Square's code. The property that lets new types plug in without editing callers.
Abstraction
Exposing what an operation does while hiding how: interfaces and abstract classes define contracts callers program against.
Interface
A contract with no state: members a type promises to implement. A class can implement many. Since C# 8 interfaces may carry default method implementations, but still no instance fields.
Abstract class
A base class that cannot be instantiated: shared state and implemented members plus abstract members children must fill in. Template for a family of types.
virtual / override / new
virtual opts a member into dynamic dispatch; override replaces it in a child; new merely hides the base member — base-typed calls still get the base version (a classic bug).
sealed
Forbids further inheritance of a class (or further overriding of a member). Communicates "not designed for extension" and enables devirtualization optimizations.
Composition
Building behavior by containing and delegating to other objects ("has-a") instead of inheriting. Swappable at runtime, testable, and free of the fragile-base-class problem.
Coupling / cohesion
Coupling: how much modules know about each other (want low). Cohesion: how focused a module's responsibilities are (want high). Most principles are strategies for these two numbers.
SRP — Single Responsibility
A class should have one reason to change. A ReportGenerator that also emails and logs has three.
OCP — Open/Closed
Open for extension, closed for modification: add new behavior as new types plugging into an abstraction, not by editing a switch in existing tested code.
LSP — Liskov Substitution
Any subtype must be usable wherever the base is expected without surprises — no strengthened preconditions, weakened postconditions, or thrown NotSupportedException (the Square-extends-Rectangle trap).
ISP — Interface Segregation
Many small client-specific interfaces beat one fat one; implementers shouldn't be forced to stub members they don't support.
DIP — Dependency Inversion
High-level policy depends on abstractions, not concrete details; the concretions are supplied from outside. What makes business logic testable and infrastructure swappable.
Dependency injection
The mechanical half of DIP: dependencies arrive through the constructor instead of being new-ed up inside. A container (like .NET's built-in one) wires the object graph.
Design pattern
A named, reusable solution shape for a recurring design problem (GoF catalog: factory, strategy, observer, decorator…). Vocabulary first, code template second.
Immutability
Objects whose state never changes after construction (C#: records, init-only setters, readonly). Safe to share across threads, safe to use as dictionary keys, trivially cacheable.

Core concepts

Interface vs abstract class

Choose an interface for a capability many unrelated types can have (IDisposable, IComparable, ILogger) — it's stateless, and a class can implement several. Choose an abstract class for a genuine family sharing state and partial implementation (Stream and its subclasses). The practical tiebreaker in modern C#: dependencies you want to mock or swap should be interfaces; DI, Moq, and the whole ASP.NET ecosystem assume it. Default interface methods (C# 8+) let interfaces evolve without breaking implementers, but interfaces still cannot hold instance fields.

Composition over inheritance

Inheritance is the strongest coupling in the language: a child inherits every implementation decision, and base-class changes ripple down blindly (the fragile base class problem). Deep hierarchies also force one axis of variation — a NotificationSender with Email/Sms children can't also vary by retry policy without combinatorial subclasses. Composition keeps each axis a separate injected component: new Sender(channel, retryPolicy). Rule of thumb: inherit only for true is-a with stable base contracts; otherwise contain and delegate. Notice .NET's own drift: LINQ composes operators; middleware composes handlers.

SOLID as daily decisions

SRP: if describing a class needs "and", split it. OCP: the switch statement you keep re-editing for each new case wants to become an interface with one implementation per case. LSP: if a subclass throws NotSupportedException from an inherited member, the hierarchy is wrong — the member belongs in a smaller interface (which is ISP). DIP: your OrderService should mention IPaymentGateway, never StripeClient. These aren't laws — a three-case switch that never grows is fine — they're pressure valves you open when change requests keep hitting the same code.

Dependency injection in practice

Constructor injection is the default: dependencies are visible, required, and the object is valid once constructed. The composition root (Program.cs) is the one place that knows concrete types — everything else sees interfaces. Benefits compound: tests hand in fakes/mocks without patching anything; implementations swap per environment (real gateway in prod, fake in dev). Smells: a constructor with eight dependencies is SRP failure, not DI failure; service-locator calls (provider.GetService<T>() sprinkled in logic) hide dependencies and defeat the point.

Patterns you already use in .NET

The GoF catalog is baked into the platform: events are the observer pattern; IEnumerable/IEnumerator is iterator; Stream wrappers (GZipStream around FileStream) are decorator; Task.Factory and ActivatorUtilities are factories; LINQ's operator chaining is a fluent builder; middleware is chain-of-responsibility; strategy is "inject a different implementation of the interface" — DI's bread and butter. Learn them as vocabulary for design conversations; reach for them when the problem shape matches, not to decorate simple code.

Equality, hashing, and identity

Reference types default to identity: Equals/== mean "same object". Value semantics must be built — override Equals and GetHashCode together (equal objects must hash equal, or dictionaries break), implement IEquatable<T>, overload operators — or just use a record, which generates all of it. Pitfalls: mutating an object while it sits in a HashSet strands it in the wrong bucket (another argument for immutable keys); string's == is overloaded to compare content, teaching beginners the wrong default for every other class.

virtual/override vs new — which method actually runs

class Animal  { public virtual string Speak() => "..."; }

Animal a2 = new Cat();  a2.Speak();  // "..."   — new: compile-time type wins!

3. Application Architecture, Frameworks & Tools

Assembling real applications: the ASP.NET Core request pipeline and its DI container, EF Core and its pitfalls, how solutions are layered so business logic survives framework churn, and the everyday toolchain — dotnet CLI, NuGet, xUnit/Moq, configuration, logging, and deployment.

Key terms

.NET SDK / runtime
The SDK builds (compilers, dotnet CLI, MSBuild, templates); the runtime only runs. Servers need the runtime (or a self-contained publish); dev machines need the SDK.
dotnet CLI
The front door to everything: dotnet new/build/run/test/add package/publish. IDEs drive the same MSBuild underneath — CI scripts use the CLI directly.
csproj / MSBuild
The project file: target framework, package references, build settings. SDK-style projects are a few lines and glob source files automatically.
NuGet
The .NET package ecosystem: versioned assemblies with transitive dependency resolution, restored at build. Your own libraries ship the same way (dotnet pack).
ASP.NET Core
The web framework: one stack for APIs, MVC sites, Razor pages, gRPC, SignalR. Cross-platform, DI-native, built around a middleware pipeline hosted by Kestrel.
Middleware
Components chained on every request: each can act, call the next, and act again on the way back (logging, auth, routing, error handling). Order of registration = order of execution.
Minimal APIs / controllers
Two dialects for endpoints: app.MapGet("/users/{id}", ...) lambdas, or controller classes with attribute routing. Same pipeline, same DI, same model binding underneath.
Model binding / validation
The framework materializes route values, query strings, and JSON bodies into typed parameters/DTOs, then runs validation attributes before your code runs.
DI lifetimes
Singleton: one instance forever. Scoped: one per request. Transient: new every resolve. The container also disposes what it creates at scope end.
EF Core
The object-relational mapper: LINQ queries become SQL, rows become tracked entities, SaveChanges turns your object edits into INSERT/UPDATE/DELETE.
DbContext
A unit of work: short-lived, not thread-safe, registered scoped. Tracks loaded entities' changes until SaveChanges.
Migration
Versioned schema change generated from model diffs (dotnet ef migrations add), applied in order to evolve the database with the code.
IConfiguration / IOptions<T>
Layered config: appsettings.json ← per-environment json ← environment variables ← user-secrets, later wins. IOptions binds a section to a typed class.
ILogger<T>
Structured logging abstraction: message templates with named placeholders ("Order {OrderId} failed") flow to console, Serilog, Application Insights, etc.
xUnit
The de-facto test framework: [Fact] for single cases, [Theory]+[InlineData] for parameterized ones, constructor/IDisposable for setup/teardown.
Moq / test doubles
Mock library: new Mock<IPaymentGateway>(), Setup(...) canned answers, Verify(...) interaction checks — possible because dependencies are interfaces.
WebApplicationFactory
Boots the real app in-memory for integration tests: real pipeline, real DI, real routing — with test-overridden services (e.g. in-memory DB) and an HttpClient.
BackgroundService
Base class for long-running hosted work (queue consumers, schedulers) living inside the app's host with DI and graceful-shutdown cancellation.
HttpClientFactory
AddHttpClient — pools handlers to avoid the classic socket-exhaustion bug (new HttpClient per request) and DNS staleness (one static client forever).
Layered / clean architecture
Domain at the center, application services around it, infrastructure (DB, HTTP, framework) at the edge; dependencies point inward via interfaces the inner layers own.
Repository / unit of work
Abstraction over persistence so domain logic doesn't reference EF Core directly. (Note: DbContext itself already is a repository+UoW — extra layers should earn their keep.)
CQRS
Separate models for writes (commands, rich domain rules) and reads (queries, shaped DTOs straight from SQL). Often via MediatR handlers; full event-sourced CQRS is a much bigger commitment.
System.Text.Json
The built-in JSON (de)serializer: fast, Span-based, source-generatable. Newtonsoft.Json remains common in older code and for exotic scenarios.

Core concepts

The request pipeline is the app

An ASP.NET Core app is a stack of middleware ending at an endpoint. Each request walks down the stack and back up — so order matters enormously: exception handling first (to catch everything below), then HTTPS/HSTS, static files, routing, CORS, authentication before authorization, then endpoints. Auth after routing but before your handler is why [Authorize] works. Cross-cutting concerns (rate limiting, tenant resolution, request logging) belong here, written once, instead of sprinkled through controllers.

DI lifetimes and the captive dependency

Scoped services (DbContext!) exist once per request; singletons live for the process. The deadly combination: a singleton that takes a scoped service in its constructor captures it — the "per-request" object silently becomes per-process, shared across concurrent requests (DbContext is not thread-safe; this produces corrupt tracking and heisenbugs). The container throws for this in development thanks to scope validation. When a singleton genuinely needs scoped work, it creates a scope: using var scope = scopeFactory.CreateScope() — the standard pattern inside BackgroundService loops.

EF Core without footguns

EF Core translates LINQ to SQL — when it can. The classics: the N+1 query (loop over orders touching order.Customer lazily = 1+N round trips; fix with Include or projection), forgetting AsNoTracking() on read-only queries (change tracking costs memory and time), filtering in memory because a .Where came after .AsEnumerable(), and long-lived contexts accumulating tracked entities. Prefer projections (Select(o => new OrderSummary(...)) that fetch only needed columns. Migrations keep schema in git; apply them by script/CI in production rather than auto-migrate on boot.

Layering that survives frameworks

The point of clean/onion layering is that business rules outlive infrastructure choices: the domain project references nothing; the application layer defines ports (IOrderRepository, IEmailSender) it needs; infrastructure implements them with EF/SMTP/HTTP; the web project is just an adapter calling application services. Dependencies point inward only — enforced by project references, so the compiler polices the architecture. Payoffs: unit tests cover rules with no database; swapping Postgres for Cosmos touches one project. Cost: indirection — a CRUD app may honestly not need more than controllers + DbContext.

A testing pyramid that works in .NET

Base: fast xUnit unit tests of domain and application logic with Moq fakes at the ports — thousands, milliseconds each. Middle: integration tests with WebApplicationFactory hitting real routing/DI/serialization, database via Testcontainers or SQLite-in-memory. Tip: a few end-to-end smoke tests. Design feedback is the hidden value: code that is hard to test (statics, new-ed dependencies, DateTime.Now inline) is coupled code — inject a clock (TimeProvider), inject the gateway. dotnet test runs it all in CI on every push.

Config, logging, deployment

Configuration layers so the same binary runs everywhere: appsettings.json defaults, appsettings.Production.json overrides, environment variables on the host, secrets in user-secrets (dev) or a vault (prod) — never in git. Structured logging with message templates makes logs queryable ({OrderId} becomes an indexed field, not string soup). Deployment: dotnet publish framework-dependent (small, needs runtime installed) or self-contained/AOT (bigger, zero prerequisites); containers standardize the rest. Health-check endpoints + graceful shutdown (host cancels BackgroundService tokens) complete the production story.

EF Core N+1 — the query you didn't know you wrote

var orders = db.Orders.ToList();              // SELECT * FROM Orders     (1 query)
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);       // SELECT ... WHERE Id = @p (N queries!)

100 orders = 101 round trips.  fixes:

eager load:   db.Orders.Include(o => o.Customer).ToList();          // 1 JOIN query
projection:   db.Orders.Select(o => new { o.Id, o.Customer.Name })  // 1 query,
                        .ToList();                                   // only 2 columns

projection also skips change tracking — ideal for read endpoints.
watch the logs: EF logs every SQL statement it sends (EnableSensitiveDataLogging
in dev) — the N+1 is obvious the moment you look.

EF Core round trip — sequence from LINQ to UPDATE

var o = db.Orders.First(o => o.Id == 7);   o.Status = "Shipped";   db.SaveChanges();

your code                DbContext / change tracker              database
   │  LINQ expression tree   │                                       │
   │ ──────────────────────▶ │  translate to SQL                     │
   │                         │ ── SELECT … WHERE Id = 7 ───────────▶ │
   │                         │ ◀──────────────────── row ─────────── │
   │ ◀── entity ──────────── │  materialize + save a SNAPSHOT        │
   │  o.Status = "Shipped"   │  (nothing sent — just a C# object)    │
   │  SaveChanges()          │                                       │
   │ ──────────────────────▶ │  diff every tracked entity vs its     │
   │                         │  snapshot → o.Status changed          │
   │                         │ ── BEGIN TX; UPDATE Orders            │
   │                         │    SET Status=@p WHERE Id=7; COMMIT ▶ │
   │ ◀── rows affected ───── │                                       │

AsNoTracking() skips the snapshot: reads get cheaper, but SaveChanges has
nothing to diff — which is exactly why it belongs on read-only queries.
One SaveChanges = one transaction: all pending changes commit or none do.

Idempotency keys — sequence of a safe retry

client                         API                          store
  │  POST /payments               │                            │
  │  Idempotency-Key: K1          │                            │
  │ ────────────────────────────▶ │  seen K1?  no              │
  │                               │ ─────────────────────────▶ │  save (K1, pending)
  │                               │  charge the card…          │
  │        ✗ timeout —            │ ─────────────────────────▶ │  save (K1, receipt R)
  │ ◀╌╌╌╌ response lost ╌╌╌╌╌╌╌╌  │                            │
  │                               │                            │
  │  RETRY — same key K1          │                            │
  │ ────────────────────────────▶ │  seen K1?  YES             │
  │                               │ ─────────────────────────▶ │  load receipt R
  │ ◀──────────────────────────── │  replay stored response    │
  │  receipt R — charged ONCE     │                            │

the timeout was ambiguous (did it run?) — the key makes the answer irrelevant:
at-least-once requests, at-most-once execution.

Transactional outbox — sequence of a reliable event

handler            orders DB               relay (BackgroundService)     broker
  │  BEGIN TX           │                          │                        │
  │ ──────────────────▶ │ INSERT order             │                        │
  │ ──────────────────▶ │ INSERT outbox row        │                        │
  │  COMMIT ──────────▶ │  ◀━ atomic: both rows or neither ━                │
  │  (request done)     │                          │                        │
  │                     │ ◀── poll undispatched ── │                        │
  │                     │ ─── rows ──────────────▶ │                        │
  │                     │                          │ ── publish event ────▶ │
  │                     │                          │ ◀───── ack ─────────── │
  │                     │ ◀── mark dispatched ──── │                        │

crash after COMMIT but before publish?  the row is still undispatched —
the relay retries on its next poll.  Nothing is ever lost; delivery becomes
at-least-once, so consumers deduplicate by event id.

Expand/contract — renaming a column under rolling deploys

goal: rename Name → FullName while old + new app versions share the database

release 1  EXPAND     ALTER TABLE ADD FullName          old code: uses Name ✓
                      new code: writes BOTH, reads Name
                      backfill: SET FullName = Name WHERE FullName IS NULL
release 2  MIGRATE    new code: reads FullName, still writes both
release 3  CONTRACT   code touches only FullName        ALTER TABLE DROP Name

deploy timeline:      v1 ▓▓▓▓▓░░░░░
                      v2      ░░░░▓▓▓▓▓░░░░
                      v3               ░░░░▓▓▓▓▓      ← during every ░ overlap,
                                                        TWO versions run at once
every intermediate schema works for both live versions — one breaking change
split into three deployable, individually reversible steps.
